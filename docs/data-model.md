# Data model

The service keeps its own data in MariaDB 10.6. Flyway owns the schema, and the migrations live in
`src/main/resources/db/migration/`. A file is named `V1_<n>__<what_it_does>.sql`, with `<n>` counting up from `0`.
`V1_0__initial_schema.sql` is a squashed baseline, and every later file changes it.

Hibernate never creates or changes tables in a deployed service: `spring.jpa.properties.jakarta.persistence.schema-generation.database.action`
is `none`. How the schema gets applied depends on the profile.

|           Profile           |             Flyway             | Hibernate schema action |          Database           |
|-----------------------------|--------------------------------|-------------------------|-----------------------------|
| default (`application.yml`) | `spring.flyway.enabled: false` | `none`                  | from the environment        |
| `it` (integration tests)    | enabled                        | `validate`              | Testcontainers MariaDB 10.6 |
| `junit` (unit tests)        | disabled                       | `update`                | Testcontainers MariaDB 10.6 |

The `it` profile is the one that proves the migrations and the entities agree: Flyway builds the schema and Hibernate
fails the start if an entity does not match it. The `junit` profile lets Hibernate build the tables from the entities,
so a unit test passes even when a migration is missing.

## Relationships between modules

- `ErrandEntity` has no JPA relation to any other module. Every other table refers to the errand through a plain
  `errand_id` column and is read through its own module's repository.
- Deleting an errand removes its rows in two ways. Tables with a foreign key to `errand` (or to
  `errand_financial_assistance` or the calculation draft) go with it through `ON DELETE CASCADE`: the financial
  assistance tables, conversation, notes, status history, form snapshot, notifications, co-caseworkers and process
  message retries. Tables with only an index on `errand_id` are cleaned up by a listener on `ErrandDeleted`, which
  `ErrandService.deleteErrand` publishes after the delete: `stakeholder` (`StakeholderErrandDeletedListener`),
  `decision` (`DecisionErrandDeletedListener`), `attachment` (`AttachmentErrandDeletedListener`), `permit`
  (`PermitErrandDeletedListener`), `referral` (`ReferralErrandDeletedListener`) and `errand_event`
  (`ErrandEventDomainListener`). These listeners run asynchronously through `@ApplicationModuleListener`, so for a
  moment the rows outlive the errand.
- `errand_financial_assistance` and `errand_financial_assistance_calculation_draft` share their primary key with
  `errand.id`. The service sets `errand_id` from the envelope; nothing generates it.
- `lookup`, `namespace_config`, `user_settings` and `errand_number_sequence` are keyed by namespace and municipality,
  not by errand.

## Changing the schema

1. Add a new file with the next number, `V1_37__<what_it_does>.sql` after `V1_36`. Never edit a file that has been
   applied: Flyway checks the checksum of every applied migration and refuses to start when one has changed.
2. Change the entity in the same commit. Run the integration tests, since only the `it` profile checks the entities
   against the migrations.
3. Ids are UUIDs stored as `varchar(36)` and mapped as `String` with `@UuidGenerator`. `attachment_data` is the
   exception, with an `AUTO_INCREMENT` id. `spring.jpa.properties.hibernate.type.preferred_uuid_jdbc_type: BINARY`
   only concerns `java.util.UUID` fields, which today means Spring Modulith's `event_publication.id` (`binary(16)`).
4. An entity that implements `shared/Auditable.java` and declares `@EntityListeners(AuditableListener.class)` gets
   `created` on insert and `modified` on update from `shared/AuditableListener.java`, in the JVM's time zone and
   truncated to milliseconds. `ErrandEntity` also sets `touched` on every insert and update, which is the default sort
   of the errand list. A bulk update through a repository query skips both.
5. Add a foreign key to `errand` with `ON DELETE CASCADE` for a new errand-scoped table, or a listener on
   `ErrandDeleted` in the owning module if the table must not depend on `errand`.
